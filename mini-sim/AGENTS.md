## 0. Artifact and release packaging — one ZIP layer only

- GitHub Actions `actions/upload-artifact` already creates the downloadable ZIP. **Never create a plugin ZIP and then upload that ZIP as an Actions artifact**; that creates ZIP-inside-ZIP.
- The Mini-Sim package workflow uploads the `mini-sim/` directory tree directly with a path pattern that preserves `mini-sim/` as the top-level folder (currently `'**/mini-sim/**/*'`). Do not add a separate `zip` packaging step.
- Do not add intermediate archive extraction, nested ZIP validation by unpacking, or user-machine staging under `%TEMP%` / `C:\\Temp`. Build and verify in the ephemeral GitHub Actions runner; the downloaded artifact itself is the one ZIP to install or extract once.
- Keep the First Planet WordPress bundle (`first-planet/wp-dist/first-planet.js` and `.css`) and the full plugin tree inside that single artifact. A missing bundle must fail the workflow before upload.

# Инструкция агентам: BCM Mini-Sim

## 1. ОБЯЗАТЕЛЬНО: сначала проверить общие задачи и Git, а не начинать с нуля

Перед любым анализом, а тем более изменением кода, выполни reconcile:

1. Прочитай `WORK_COORDINATION.md`, `PROJECT_STATE.md` и `DECISIONS.md`. Они описывают протокол совместной работы, активный этап и уже выполненные решения.
2. Просмотри открытые GitHub Issues и Pull Requests. Ищи активные `WORK LOCK`-задачи и проверь, не затрагивает ли незавершённая ветка те же файлы или общий API. Если задача не забронирована, создай Issue `WORK LOCK: ...` до первого изменения кода.
3. Проверь текущий `main`/HEAD, ветку своей лаборатории и коммиты после `Last reconciled repository HEAD` из `PROJECT_STATE.md`. В терминале используй `git log --oneline --decorate -20` и `git log --oneline <baseline>..HEAD`; без терминала сверяй GitHub Commits, diff и активные PR.
4. Открой диффы релевантных коммитов и сопоставь их с текущим кодом и тестами. Название коммита — свидетельство намерения, но не доказательство поведения в браузере.
5. Определи статус задачи до правок. Не повторяй исправление без свежего воспроизводимого свидетельства регрессии. Если другой агент ещё работает в той же области, не перезаписывай его незакоммиченные результаты: согласуй границы/передачу через общий Issue.
6. Только после сверки назови минимальный набор файлов, добавь проверку и сделай ограниченный патч. **Актуальная директива владельца от 14.11.2026 для BCM4StarAtlas: работай непосредственно в `main`; не создавай feature-ветки и PR без нового прямого разрешения владельца.**

**Git — память выполненной работы; Issues/PR — общий видимый контекст. Для этого проекта действует более поздняя директива владельца: изменения выполняются прямо в `main`; одновременно только один writer, остальные AI-агенты работают как read-only reviewer/tester.** Не затирай незакоммиченные результаты другого агента и не начинай конфликтующую запись.

### 1.1 Проверка Shell и резервный путь без терминала

Перед запуском npm, curl, Playwright или изменением файлов проверь **сам инструмент Shell**, а не только команды внутри него.

- Если Shell отсутствует в списке инструментов агента, это `SHELL-UNAVAILABLE`. Никакая правка репозитория не выдаст агенту недостающий инструмент или разрешение платформы.
- Если Shell присутствует, выполни один короткий preflight: `pwd`, затем `node -v`. Если вызов инструмента не запускается, зависает или возвращает только оболочечное сообщение без stdout/stderr, повтори максимум один простой вызов и остановись. Не зацикливайся на `pwd`, `curl`, `npm` и клонировании.
- Классифицируй причину по фактическому сообщению: `SHELL-UNAVAILABLE` (сам инструмент), `OS-PERMISSION` (`Permission denied`), `NODE-INCOMPATIBLE` (например, `bad option`), `NETWORK-BLOCKED` (DNS/connection), `HTTP-BLOCKED` (HTTP 401/403/429), `BROWSER-MISSING` (Playwright не находит Chromium), `GITHUB-WRITE-UNAVAILABLE` (GitHub API отказал в записи). Не называй всё это одним словом «Shell blocked».
- Если Shell недоступен, не проси владельца повторять команды и не объявляй проект сломанным. Перейди к доступному GitHub read-only интерфейсу; передай writer'у конкретный файл/символ, diff-предложение и критерии проверки.
- **Единственный writer по текущему прямому указанию владельца — DR GPT в сессии с подключённым GitHub write-инструментом.** Он сверяет HEAD и рабочие блокировки, вносит изменения и пишет в `main`. Dr Fable, Grok, Einstein и прочие агенты считаются read-only reviewer/tester, пока владелец явно не изменит распределение прав и их запись не будет реально проверена.
- Для runtime-проверок используй существующие GitHub Actions, которые запускаются push в `main`; после коммита writer проверяет статусы и логи именно для полученного SHA. Не записывай тесты как PASS до получения результата Actions. Для Mini-Sim локальный браузерный сценарий — `npm run qa:minisim:standalone`; корневой `npm run dev` запускает Galia, а не Mini-Sim.
- Live WordPress browser QA остаётся выключенным по ранее данному владельцем указанию. Однократный HTTP 200 от обычного клиента не доказывает, что Playwright проходит защиту, и сам по себе не разрешает восстанавливать live-QA или менять firewall.

## 2. Статусы задач и как трактовать молчание пользователя

Используй одинаковые статусы во всех сессиях и для всех агентов:

- **IMPLEMENTED** — изменение есть в текущем коде/коммите. Не означает, что оно проверено в браузере.
- **TESTED-CODE** — автоматические тесты/линтеры прошли на указанном SHA. Не означает, что игра нормально работает на сайте.
- **VERIFIED-LIVE** — поведение подтверждено на конкретной версии сайта/окружения.
- **USER-CONFIRMED** — пользователь явно сообщил, что конкретный сценарий работает.
- **OPEN** — исправления нет или есть конкретное воспроизводимое несоответствие.
- **NEEDS-USER-STATUS** — код выглядит готовым, но для решения текущей задачи существенно неизвестно, подтверждал ли пользователь живое поведение. Задай один короткий вопрос только тогда, когда ответ влияет на следующий шаг.
- **BLOCKED** — есть конкретный недостающий доступ, файл, источник или воспроизводимый вход.
- **REOPENED** — ранее закрытый пункт снова имеет конкретное доказательство регрессии; укажи новое свидетельство и commit/SHA.

Правила:

- **Молчание не равно подтверждению**, но также не равно доказательству, что работа не сделана. Если пользователь переходит к другой задаче, не объявляй прежний пункт нерешённым только из-за отсутствия похвалы/ответа.
- Если есть текущая реализация и тест, не переписывай код из-за одной старой записи. Сначала проверь текущий код и историю.
- Если код говорит, что исправление реализовано, но живой тест не известен, сохрани статус **IMPLEMENTED / live status unknown**. Когда это влияет на работу, спроси пользователя о точном сценарии; не делай вид, что есть подтверждение.
- Если пользователь явно сказал «работает», переведи в **USER-CONFIRMED**, зафиксируй что именно и в каком сценарии. Не возвращай задачу в OPEN без нового свидетельства.
- Когда пользователь сообщает новый дефект, добавь его как новый репорт/свидетельство и сравни с последним подтверждённым коммитом. Если поведение было исправлено более поздним коммитом, проверь, тестирует ли пользователь эту версию сайта.
- Не спрашивай повторно о статусе, который однозначно подтверждён записью в текущем журнале; не проси пользователя искать то, что можно проверить в коммитах или исходниках.

## 3. Порядок работы над этапом

1. Сверь коммиты и журнал решений (раздел 1).
2. Прочитай этот файл и актуальные разделы `PROJECT_STATE.md`.
3. Найди минимальные точки входа поиском по символам/событиям. Не перечитывай весь репозиторий и не переписывай модуль целиком ради локального исправления.
4. Работай только над активным этапом. Не смешивай аудио, управление, карту SAGE, Tube и Room0-лабиринт в один патч.
5. До изменения назови проверяемый результат и необходимые файлы. Сначала проверь потребителей общего API (музыка, ввод, переходы, система координат), не ограничивайся найденным вызовом.
6. Внеси ограниченное изменение, добавь/обнови регрессионный тест и выполни доступные проверки.
7. Обнови `PROJECT_STATE.md` и добавь или уточни запись в `DECISIONS.md`, включая SHA коммита, статус и доказательства.
8. Разделяй статическую проверку исходников, автоматизированный browser test, реальный сайт и ручную игровую проверку. Не заявляй более сильный уровень, чем реально выполнен.

## Правило небольших изменений

- Один активный этап = один ограниченный набор связанных изменений.
- По возможности один функциональный патч/коммит за раз; после него — проверки и запись результата.
- Не меняй интерфейс, геометрию, физику, аудио или ассеты «заодно».
- Сохраняй существующие публичные события, API и WordPress-контракт, если изменение контракта не является задачей.
- Не добавляй большие библиотеки, тяжёлые ассеты или второй WebGL-контекст без необходимости.
- Не восстанавливай старое поведение только потому, что оно записано в исторической версии README. Последние требования пользователя и текущее состояние журнала важнее старой истории.

## Обновление инженерного контекста обязательно

После любой существенной работы, даже если пользователь не попросил документацию отдельно:

- обнови `PROJECT_STATE.md`: активный этап, baseline SHA, статусы, что изменено и что осталось;
- внеси/обнови запись в `DECISIONS.md`: что сделано, чем подтверждено, последующие изменения и условия переоткрытия;
- укажи commit SHA и ссылку на него, когда изменение закоммичено;
- не затирай известные работающие сценарии и подтверждённые пользователем решения;
- не переноси незавершённую историческую задачу в текущий этап, если пользователь её не переоткрыл и нет нового свидетельства;
- перед сдачей работы укажи следующий шаг, который логически следует из текущего этапа.

## Формат отчёта по задаче

- **Этап:** ID и название.
- **Сверка коммитов:** какие связанные коммиты рассмотрены.
- **Статус до изменения:** IMPLEMENTED / TESTED-CODE / VERIFIED-LIVE / USER-CONFIRMED / OPEN / NEEDS-USER-STATUS / BLOCKED / REOPENED.
- **Изменено:** файлы и поведение.
- **Проверено:** точные команды/сценарии, SHA и результат.
- **Не проверено:** что нельзя подтвердить имеющимися тестами.
- **Регрессии/следующий шаг:** конкретные пункты, без общих обещаний.
